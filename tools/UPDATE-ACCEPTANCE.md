# Обновление движка с сохранением обязательных правок

Проверяются две независимые границы. `check_required_layers.py` вычисляет
результат точного рецепта из подписанного архива и закреплённого Steam-кода.
Контракт проверяет 13 обязательных групп, включая авторизацию, lifecycle,
приглашения, меню/команды, скины, список миров, заголовок, значок и native UI уведомлений. Комментарий
вместо вызова не проходит проверку. Это проверка исходников, а не доказательство
игрового поведения. Отдельный слой держит Steam-раздел по умолчанию, явный
доступ к полному сохранённому списку, отсутствие записи NBT при просмотре и
привязку выбранного Steam-мира к адресу вместо номера изменяющейся строки.

`release_acceptance.py` проверяет отчёты поведения, привязанные к полному
инвентарю исполняемых файлов/данных, upstream/Steam pins и квитанции рецепта.
Свежесть означает совпадение этих входов, а не возраст файла отчёта. HEAD,
описание библиотеки и превью не входят в эту привязку. Поэтому QA-only и
редакционные коммиты не заставляют повторять игровой прогон.

## Порядок

1. В чистом worktree перенести рецепт на новые подписанные исходники. Любой
   конфликт обязательного слоя остановит подготовку. Проверить исходники:

   ```powershell
   python tools/check_required_layers.py --archives $archives `
       --steam-transport $steamRepo/source/native --out tools/required-layer-proof.json
   ```

2. Собрать и получить обычную overlay-receipt; подготовить candidate штатным
   stage_runtime. Он повторно вычисляет послепроверки и сверяет результат
   с квитанцией и required-layer-proof. Архивы, код мода и Java/Mojang кеши
   переиспользовать; игровые папки держать отдельно в зарегистрированном стенде.

   Bootstrap проверяется отдельно по `tools/bootstrap-lock.json`: Cargo manifest,
   lock, имеющиеся `.cargo/config`/`config.toml`/`build.rs`, все Rust-файлы `src`,
   fingerprint отсортированного списка, release/MSVC x64/static CRT и EXE SHA-256.
   Для sourceFiles/sourceSha256 использовать `bootstrap_contract.bootstrap_sources`
   и `source_fingerprint`; данные сборки записываются после настоящей компиляции.
   Политика `launcher/environment-defaults.json` должна совпадать с
   `native/presentation.json:environmentDefaults`. Потеря vendor opt-out Overwolf
   при авторском обновлении, старый bootstrap или несовпадение политики блокируют
   staging/упаковку. Реестр и чужие процессы для обхода проверки не менять.

3. Проверить точный candidate через `smoke_runtime.py --bootstrap ... --cache ...
   --expect-title 'Minecraft Rust Edition' --expect-cold --check-pause-menu` без
   `--minecraft`/`--java`, затем `steam_runtime_qa.py`. Оба инструмента сохраняют
   acceptanceContext до запуска и проверяют неизменность файлов после прогона.
   Для неизменившегося подготовщика можно использовать прежний отдельный cold
   proof, только если SHA bootstrap/preparer/research и resource receipt совпадают.

   При изменении bootstrap или policy нужна новая приёмка. Подтвердить применение
   defaults реальным bootstrap к его дочернему клиенту и результат запуска,
   сохранив Vulkan и Steam. Только вручную добавленная переменная в QA-процесс
   не доказывает доставку исправления. Общий bootstrap сохраняет явно заданные
   переменные, включая пустые; повторение значений в C# лаунчера не требуется.

4. Запустить `tools/server_list_qa.py --candidate $candidate --controller $controller
   --resources $resources --out $serverQa --ui-key-requests $serverQa/ui-keys`, затем использовать
   `$serverQa/server-list-qa.json` как `$serverList`. Проверка делает шесть обычных
   запусков без CLI-флагов harness: новый пустой список дважды, ручной NBT дважды,
   затем старые неоднозначные рекомендации вместе с ручным сервером дважды.
   Последняя пара проверяет Steam-раздел по умолчанию, явный переход к сохранённым
   серверам, сброс скрытого выбора, ручной ввод, повторный вход через заглавный
   экран и побайтовую сохранность неизвестного NBT и старых маркеров.
   На пятом и шестом запусках обслужить по семь запросов `.request.json` из
   `ui-keys`: Enter, Delete, F5, F5, Ctrl+A, Backspace, Enter. Перед каждым
   действием UI-драйвер заново находит настоящее окно указанного `processId`,
   сверяет его путь и заголовок и получает свежий снимок, затем нажимает клавишу.
   После действия атомарно записывает одноимённый `.ack.json` с `id`, `key`,
   `processId`, `status: "PASS"` и фактическим `performedUnixMs` (Unix ms).
   Запрос содержит `action: "press_key"`, путь EXE, заголовок, номер запуска и
   срок 120 секунд; чужой или просроченный ответ отклоняется. Эти ключи идут
   через настоящее окно: авторский key RPC на заглавном экране требует мир.
   Обычный smoke с `--control-socket` пропускает авторский startup seeding и не
   заменяет эту проверку. Source guard запрещает возвращение обоих startup-вызовов,
   а выпуск требует свежий отчёт обычного запуска для полного candidate. При
   обновлении автора новый seeding или каталог надо проверить и перенести этот
   эффект, не очищая личный список по именам/адресам/маркерам.

   Запустить также `tools/native_notices_qa.py --candidate $candidate
   --controller $controller --cache $cache --out $noticeQa`; использовать
   `$noticeQa/native-notices-qa.json` как `$nativeNotices`. Он проверяет настоящий
   bootstrap/дочерний PID, финальные PNG и свежий post-present heartbeat в меню,
   мире и полном экране, очередь/срок жизни/будущее время/оборванные файлы, DPI и
   сохранность ввода/GUI scale/session.json/состава модов. Один heartbeat без
   захваченных пикселей не считается доказательством. Снимки `--scaled` и
   offscreen не заменяют реальный оконный frontend.

   Поле `timing` сохраняет реальные `createdUnixMs`/время записи и наблюдения
   heartbeat: три карточки ещё показаны после шестой секунды и исчезают после
   исходных 7000 мс; два повреждённых снимка подаются после второй и четвёртой
   секунд и не продлевают этот срок. Нулевой post-present heartbeat должен быть
   получен не позже 1000 мс после исходного срока, с учётом его шага 500 мс.
   Для будущего уведомления фиксируются входные +1500 мс, пустой кадр до создания
   и видимый кадр после него без повторной записи очереди. Gate сверяет эти
   интервалы со временем PNG и обоих heartbeat, а не только с метками PASS.
   `dpi` содержит измеренные ширины из PNG и реальные GUI scale/UI до и после;
   проверяется ширина 240/480 пикселей и масштаб ровно два без изменения игры.

   Записать пакет доказательств; coldPreparation берётся из холодного smoke,
   либо отдельного --preparation. До проверки обновления --update можно опустить.

   ```powershell
   python tools/release_acceptance.py --candidate $candidate --smoke $smoke `
       --multiplayer $multiplayer --servers $serverList --native-notices $nativeNotices `
       --out tools/release-acceptance.json `
       --defer-live-steam 'Точное сохранённое решение пользователя'
   ```

   Отсрочка допустима только по действующему решению пользователя. После живого
   прогона вместо неё передать --live-steam-report: PASS, acceptanceContext и
   checks.shiftTab/invitation/twoAccountJoin = PASS. Результаты не выдумывать.

5. Принять inventory/preview/distribution lock обычным способом и закоммитить
   исходники. `generate_manifest.py --prepare-qa` создаст архивы и
   **candidate-manifest.json**, без выпускного pack-manifest. Передать эту папку
   и предыдущую поставку NativeUpdateQa: он читает оба имени манифеста. Проверить
   прерывание загрузки, блокировку клиента, отказ запуска неполного набора,
   повторную попытку и сохранность настроек/серверов/прогресса.

6. Повторить команду пункта 4 с --update $updateReport. Инвентарь targetFiles и
   SHA runtime-архива отчёта должны соответствовать всему выпускаемому набору,
   включая отдельный архив пресета. Сохранить доказательства в Git. Обычные
   generate_manifest и --verify-only теперь требуют все обязательные отчёты.
   После QA-only коммита SHA игровых архивов должен остаться прежним.

7. До активации манифеста с `native-launcher-notices-v1` проверить опубликованный
   поддерживающий EXE лаунчера и его SHA-256. Технический NativeUpdateQa также
   собирать из поддерживающей ревизии лаунчера, а не из прежней без capability.
   Общий EXE выпускает владелец реализации лаунчера; данные сборки не повышают
   его номер отдельно. Затем опубликовать архивы, независимо скачать их и проверить SHA-256, затем
   опубликовать манифест последним и проверить его обратным скачиванием.

## Текущая принятая поставка

Текущая запись получена прямыми Windows-прогонами клиента `c6640181` на
подписанном Horizon `2ebf00a`, с сохранением мира, обоими гостевыми сценариями,
числовым портом в чате, шестью обычными запусками сетевого списка и 13 снимками
уведомлений. Холодная подготовка новым штатным подготовщиком сохранена отдельно;
последующая сборка клиента использует те же bootstrap/preparer/research и квитанцию
ресурсов. Проверка обновления от опубликованной `bb8302b` сохранила семь личных
файлов и не скачивала данные повторно; runtime-архив имеет SHA-256 `5133a017`.
Исторический импорт прежней поставки сохранён в Git. Живой Steam остаётся
NOT RUN по решению пользователя от 8 ноября 2026 года. Значок заголовка проверен
визуально; оба слота и семь кадров закреплены исходниками и PE-проверкой, сама
панель задач не попала в ограниченный снимок окна.

Проверки защиты без игры/Cargo:

```powershell
python -m unittest discover -s tools -p 'test_required_layers.py' -v
python -m unittest discover -s tools -p 'test_release_acceptance.py' -v
```

### Наблюдение окна при проверке клавиш

Для клавиатурных сценариев используйте текстовое состояние Sky (`include_screenshot: false`, `include_text: true`) и штатный `horizon-ctl ui`. Повторные захваты WGC во время интерактивной проверки сопровождались сообщением пользователя о мерцании; после остановки ввода и захвата оно прекратилось. Окончательный прогон выполнен без WGC и без изменения графических настроек.
